## Назначение и область действия

Этот файл определяет **структуру, правила и содержание документации Library API**. Он является основной точкой входа для разработчиков и ИИ-агентов, которым необходимо понять публичный интерфейс библиотеки или изменить его.

Документ должен отвечать на следующие вопросы:

1. За что отвечает конкретный класс или модуль и к какой части архитектуры он относится?
2. Какие публичные методы, свойства, события и типы он предоставляет?
3. Как правильно использовать каждый публичный член API?
4. Какие зависимости, ограничения, условия вызова и побочные эффекты существуют?
5. Какие другие компоненты связаны с ним и где найти их документацию?

Документ описывает **публичный контракт библиотеки**, а не внутреннюю реализацию. Приватные поля, вспомогательные методы и детали алгоритмов не включаются в API-документацию, если они не влияют на использование публичного интерфейса.

Документация ведётся в формате **Markdown (`.md`)**. Другие форматы для Library API не используются.

## Архитектура библиотеки

Верхний уровень документации разделён на три категории. Категория определяется архитектурной ролью компонента, а не только его названием или расположением файла.

```text
Library API
├── Core
│   └── CoreController
├── CoreModules
│   ├── CheckGround
│   └── ActionController
└── GameModules
    ├── MovementController
    │   └── UnderModuleForMovementController
    └── AnimationController
```

### Роль категории Core

**Core** содержит фундаментальные типы и механизмы библиотеки, на которых строятся остальные компоненты.

К этому уровню относятся базовые контроллеры, общие контракты и инфраструктура, необходимые нескольким модулям.

Принципы:

- Core не должен зависеть от конкретной игровой логики из `GameModules`.
- В Core следует размещать только действительно общие механизмы, а не функции отдельной игровой системы.
- Изменения Core могут затрагивать множество зависимых компонентов, поэтому его публичный контракт необходимо описывать особенно тщательно.

### Роль категории CoreModules

**CoreModules** содержит общие модули и сервисы, расширяющие базовые возможности Core.

Такие компоненты могут предоставлять функциональность, используемую разными игровыми системами: например, проверку состояния окружения или управление доступностью действий.

Принципы:

- Модуль должен иметь чётко определенную область ответственности.
- Общие модули не должны без необходимости знать о конкретных реализациях `GameModules`.
- Зависимости и способ подключения модуля к Core должны быть явно описаны.

### Роль категории GameModules

**GameModules** содержит компоненты, реализующие конкретные игровые системы и поведение объектов.

Например, контроллер движения может объединять подмодули ходьбы, прыжка и других вариантов перемещения. Контроллер анимации отвечает за отдельную игровую систему и может иметь собственные подмодули.

Принципы:

- Игровой модуль может использовать возможности Core и CoreModules.
- Вложенные подмодули документируются внутри родительского модуля, если они являются его частью по архитектуре и публичному контракту.
- Если подмодуль предназначен для самостоятельного использования, это необходимо явно указать.
- Связи между родительским модулем и подмодулями должны быть отражены в обеих соответствующих карточках API.

### Иерархия и расположение компонентов

Структура документации должна отражать архитектуру проекта и, насколько это возможно, повторять структуру каталогов исходного кода.

Например, если исходники организованы так:

```text
Core/
  CoreController.cs

CoreModules/
  CheckGround.cs
  ActionController.cs

GameModules/
  MovementController.cs
  MovementControllerModules/
    UnderModuleForMovementController.cs
  AnimationController.cs
```

то документация должна сохранять ту же логическую группировку. Пример выше иллюстрирует принцип: **фактические пути необходимо сверять с репозиторием**, а не копировать из примера без проверки.

## Правила документирования API

### Что считается публичным API

В документацию включаются все элементы, которыми предполагается пользоваться за пределами внутренней реализации компонента:

- публичные классы, структуры, интерфейсы и перечисления;
- публичные конструкторы;
- публичные методы;
- публичные свойства и индексаторы;
- публичные события и делегаты;
- публичные поля, если они намеренно являются частью контракта;
- важные атрибуты, generic-параметры и связанные типы, влияющие на использование API.

Сам по себе модификатор `public` не означает, что элемент обязательно является поддерживаемой частью Library API. Если элемент открыт только для технических причин или не предназначен для использования сторонним кодом, это следует явно обозначить в документации либо рассмотреть изменение его доступности.

Не следует документировать приватные и внутренние детали как гарантированную часть контракта. Если описание внутреннего механизма необходимо для понимания ограничений публичного API, его можно кратко привести в разделе «Примечания».

### Структура документации компонента

Каждый компонент (скрипт, класс, интерфейс или иной публичный тип) оформляется отдельным подразделом внутри своей архитектурной категории.

Описание компонента должно включать следующие разделы:

1. **Назначение.** Краткое описание задачи компонента и его зоны ответственности.
2. **Расположение.** Фактический путь к исходному файлу и namespace.
3. **Тип и связи.** Базовый тип, реализуемые интерфейсы, родительский модуль и подмодули, если они есть.
4. **Зависимости.** Необходимые компоненты, ссылки на них и условия их наличия.
5. **Жизненный цикл.** Когда компонент создаётся, инициализируется, используется и освобождает ресурсы, если это применимо.
6. **Публичный API.** Описание каждого публичного члена по правилам ниже.
7. **Ограничения и примечания.** Важные особенности, порядок вызовов, побочные эффекты и известные ограничения.
8. **Связанные компоненты.** Ссылки на другие разделы документации.

Неактуальные разделы не нужно заполнять формальными фразами. Если, например, у компонента нет событий или особого жизненного цикла, достаточно указать это один раз или опустить неприменимый подраздел.

### Структура описания члена API

Каждый публичный член описывается отдельно. В качестве заголовка используется его фактическое имя и, для методов, сигнатура.

Описание метода должно содержать:

- **Назначение:** что делает метод и в каких случаях его следует вызывать.
- **Сигнатура:** точная сигнатура из исходного кода.
- **Параметры:** имя, тип, назначение, допустимые значения и поведение при `null`, если применимо.
- **Возвращаемое значение:** тип и смысл результата; отдельно указать, может ли результат быть `null`.
- **Примеры:** не менее двух осмысленных примеров использования.
- **Исключения и ограничения:** какие исключения могут возникнуть, какие условия должны быть выполнены и какие вызовы недопустимы.
- **Примечания:** побочные эффекты, влияние на состояние объекта, порядок вызова и другие существенные особенности.

Для свойств, событий и типов состав разделов адаптируется:

- **Свойство:** назначение, тип, доступность чтения и записи, побочные эффекты getter/setter, допустимые значения и примеры.
- **Событие:** назначение, тип делегата, момент вызова, данные события, правила подписки и отписки, примеры.
- **Конструктор:** назначение, параметры, начальное состояние объекта, исключения и примеры создания.
- **Перечисление:** смысл каждого значения и условия его применения.
- **Интерфейс:** назначение контракта, обязательные реализации его членов и пример реализации.

Если член перегружен, каждая существенная перегрузка описывается отдельно. Нельзя объединять разные сигнатуры в одно описание, если у них различаются поведение или ограничения.

### Требования к примерам

Для каждого метода необходимо привести **минимум два примера**. Примеры должны показывать разные уместные сценарии использования, а не повторять один и тот же вызов с незначительными изменениями.

Примеры должны:

- соответствовать текущей сигнатуре API;
- использовать реальные имена типов и членов;
- содержать необходимые `using` и контекст, если без них пример непонятен;
- быть достаточно полными, чтобы читатель мог понять, куда поместить код;
- демонстрировать рекомендуемый способ использования, а не обходные решения;
- не ссылаться на несуществующие типы, методы или поля.

Для свойств, событий и типов также следует приводить примеры. Если два различных сценария действительно применимы, нужно показать оба. Если второй пример не имеет практического смысла, это следует кратко отметить, а не создавать искусственный пример.

Пример оформления:

```csharp
// Пример 1: основной сценарий использования.
// Здесь должен находиться проверенный код, соответствующий реальной реализации API.
```

```csharp
// Пример 2: альтернативный или дополнительный сценарий использования.
// Здесь должен находиться проверенный код, соответствующий реальной реализации API.
```

> Примеры выше показывают только формат оформления. Их нельзя считать примером вызова конкретного метода библиотеки.

### Исключения и ограничения

В этом разделе необходимо фиксировать не только исключения C#, но и любые условия, которые могут привести к неправильному использованию API.

Указывайте, когда это применимо:

- тип исключения и условие, при котором оно возникает;
- допустимость передачи `null`;
- поведение при некорректном или неинициализированном объекте;
- необходимость предварительной инициализации;
- допустимый порядок вызовов;
- ограничения Unity lifecycle (например, допустимость вызова до или после определённого события жизненного цикла);
- требования к главному потоку Unity;
- возможность повторного вызова метода;
- последствия повторной подписки на событие;
- изменения состояния объекта и другие побочные эффекты;
- владение объектами и ответственность за освобождение ресурсов, если применимо.

Не следует обещать исключение, если реализация вместо него использует проверку, возвращает `false`, игнорирует операцию или выводит предупреждение. Документация должна описывать **фактическое поведение**, а не предполагаемое.

Если ограничений или исключений нет, укажите: `Не выявлено` — только после проверки реализации.

## Правила навигации и оформления

Документация должна оставаться удобной для чтения как человеком, так и ИИ-агентом.

1. Используйте заголовки Markdown в соответствии с иерархией: `#` — документ, `##` — архитектурная категория или крупный раздел, `###` — компонент, `####` — член API.
2. Сохраняйте фактическое написание идентификаторов C# и заключайте имена типов, методов, свойств и параметров в обратные кавычки: `CoreController`, `Initialize()`, `CoreModules`.
3. Для переходов между компонентами используйте относительные Markdown-ссылки на разделы этого файла или на другие Markdown-файлы репозитория.
4. Для перехода к исходному коду указывайте проверенный относительный путь к файлу. При возможности добавляйте ссылку на файл и строку в интерфейсе GitHub.
5. Используйте таблицы для кратких справочных сведений: параметры, значения перечислений, статусы и зависимости. Большие описания в таблицы не помещайте.
6. Используйте блоки кода с указанием языка, например `csharp` или `text`.
7. Не дублируйте полное описание одного и того же члена в нескольких местах. В других разделах используйте ссылку на основное описание.
8. Для поиска используйте короткие теги в конце карточки компонента. Например: `Tags: #core #controller #initialization`. Теги дополняют заголовки и ссылки, но не заменяют их.
9. Поддерживайте содержание документа в актуальном состоянии после добавления, удаления или перемещения разделов.

Рекомендуемая схема имени тега: строчные латинские буквы, слова через дефис. Используйте только полезные и устойчивые теги, а не теги для каждого отдельного параметра.

## Шаблон документации компонента

Скопируйте шаблон для нового компонента и заполните его по фактической реализации. Удалите неприменимые пункты. Не оставляйте фиктивные сигнатуры или примеры.

```markdown
### ComponentName

Краткое описание назначения компонента: какую задачу он решает, за что отвечает и чего намеренно не делает.

**Категория:** `Core` / `CoreModules` / `GameModules`  
**Исходный файл:** `проверенный/относительный/путь/ComponentName.cs`  
**Namespace:** `Project.Namespace`  
**Тип:** `class` / `struct` / `interface` / `enum`  
**Наследование и интерфейсы:** `BaseType`, `IInterface`  
**Статус API:** `Stable` / `Experimental` / `Deprecated` (если проект использует такие статусы)

## Порядок внесения изменений

Любое изменение публичного контракта должно сопровождаться проверкой и обновлением документации.

### Перед изменением API

1. Прочитать этот документ целиком.
2. Найти фактическую реализацию компонента и все места его использования.
3. Проверить сигнатуры, модификаторы доступа, типы параметров и возвращаемых значений, ограничения и жизненный цикл.
4. Определить, к какой архитектурной категории относится компонент и не нарушает ли изменение направление зависимостей.
5. Проверить, какие другие компоненты и примеры будут затронуты.

### После изменения API

1. Обновить карточку компонента и описание каждого изменённого публичного члена.
2. Добавить или исправить не менее двух примеров для каждого метода.
3. Обновить сведения об исключениях, ограничениях, побочных эффектах и жизненном цикле.
4. Обновить каталог, содержание, теги и внутренние ссылки, если структура изменилась.
5. Проверить, что все имена и сигнатуры совпадают с исходным кодом.
6. Удалить документацию для удалённых членов либо явно отметить их как устаревшие, если они временно сохраняются для совместимости.

### Правила достоверности

- Исходный код является источником истины для фактических сигнатур и поведения.
- Если код и документация расходятся, нельзя автоматически считать документацию правильной: сначала необходимо выяснить, является ли расхождение ошибкой документации или реализации.
- Не придумывайте публичные члены, исключения, гарантии и поведение, которых нет в исходниках.
- Не описывайте внутренние детали как гарантированную часть публичного контракта.
- Если поведение неясно, укажите, что оно требует проверки, и не выдавайте предположение за факт.
- Документация и примеры должны соответствовать текущей версии проекта.
